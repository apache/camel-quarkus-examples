= HTTP with Post-Quantum Cryptography (PQC): A Camel Quarkus example (Java 25)
:cq-example-description: An example that shows how to implement quantum-resistant TLS using the JDK's own hybrid X25519MLKEM768 key exchange, configured through the Quarkus TLS registry, without Bouncy Castle

{cq-description}

This example serves a Camel `platform-http` endpoint over mutual TLS 1.3 protected by the hybrid post-quantum key exchange **X25519MLKEM768** (classical X25519 ECDH combined with ML-KEM-768, NIST FIPS 203).

Unlike the `http-pqc-j21` example, it uses **no Bouncy Castle at all**:

[cols="1,2,2"]
|===
| | `http-pqc-j21` | `http-pqc-j25` (this example)

| TLS provider
| Bouncy Castle JSSE, registered in code
| JDK SunJSSE

| PQC configuration
| `jdk.tls.namedGroups` system property
| Quarkus TLS registry: `quarkus.tls.pqc-enforcement-policy` (JDK default named groups)

| Certificates
| Generated at startup with the Bouncy Castle X.509 API
| Generated at build/test time with the SmallRye certificate generator

| Extra runtime dependencies
| `camel-quarkus-support-bouncycastle`, `bctls-jdk18on`
| none
|===

NOTE: TLS is pure JDK. Bouncy Castle is used only at build and test time, by the SmallRye certificate generator (Maven plugin and the `test` scoped `smallrye-certificate-generator-junit5`). It is not on the application classpath: `mvn dependency:tree -Dscope=runtime` and `target/quarkus-app/lib` contain no Bouncy Castle jar.

IMPORTANT: Requires a JDK with X25519MLKEM768 in SunJSSE (https://openjdk.org/jeps/527[JEP 527]): **JDK 25.0.5 (October 2026 update) or newer, or JDK 27+**. On older JDK 25 builds the application fails at startup with `PQC enforcement policy ... requires X25519MLKEM768 but the configured SSL engine does not support it`. Check your JDK (the output must contain `X25519MLKEM768`):

[source,shell]
----
echo 'System.out.println(String.join(",", javax.net.ssl.SSLContext.getDefault().getSupportedSSLParameters().getNamedGroups()))' | jshell -q
----

The tests detect the support at runtime (`PqcSupportedCondition` checks the JDK's supported TLS named groups) and are skipped on JDKs without X25519MLKEM768, e.g. JDK 25.0.0 - 25.0.4. The tests also require JDK 25 (`@EnabledForJreRange`). On JDK 21 (CI) the module is compiled with `release` 21 and the tests are skipped.

TIP: Check the https://camel.apache.org/camel-quarkus/latest/first-steps.html[Camel Quarkus User guide] for prerequisites and other general information.

== Configuration

The whole PQC setup is in `src/main/resources/application.properties`:

[source,properties]
----
quarkus.tls.protocols = TLSv1.3
quarkus.tls.ssl-engine = jdkssl
quarkus.tls.pqc-enforcement-policy = client-negotiated
----

`quarkus.tls.pqc-enforcement-policy` values:

* `client-negotiated` (default here): X25519MLKEM768 is accepted (JDK 25.0.5+ offers it by default), classical clients can still connect. Use it for gradual migration.
* `strict`: X25519MLKEM768 is required, only post-quantum hybrid groups are accepted, classical clients are rejected.
* `relaxed` (Quarkus default): PQC is neither enforced nor checked at startup. Do not use it for this purpose.

Both `client-negotiated` and `strict` fail at startup when the JDK does not support X25519MLKEM768, so the server never silently falls back to classical-only TLS.

== Mutual TLS and certificates

The server requires a client certificate (`quarkus.http.ssl.client-auth = required`) and trusts only the demo client certificate (`quarkus.tls.trust-store`), in both the default and the `strict` setup. Clients without a certificate are rejected during the TLS handshake.

For running the application by hand, the Maven build (`generate-resources` phase) creates demo certificates in `target/certs/` with the `smallrye-certificate-generator-maven-plugin` (password `changeit`, valid 365 days):

* `pqc-keystore.p12`, `pqc-server-truststore.p12` - server identity (`CN=localhost`, SAN `localhost`, `127.0.0.1`) and trusted client
* `pqc-client-keystore.p12`, `pqc-client-truststore.p12` - client identity and trusted server
* `pqc.crt`, `pqc-client.crt`, `pqc-client.key`, `pqc-client-ca.crt`, ... - the same in PEM form (e.g. for `curl`)

The tests generate their own certificates in `target/test-certs/` (`@Certificates` on `AbstractPqcTest`) and use them via the `%test` profile.

The generated keys and the `changeit` passwords are for demo only, do not reuse them.

The certificates use classical RSA signatures. The post-quantum protection comes from the key exchange, which defeats "harvest now, decrypt later" attacks on recorded traffic.

== Start in Development Mode

[source,shell]
----
mvn clean compile quarkus:dev
----

The application starts on a random HTTPS port with mutual TLS. Look for `Listening on: https://localhost:xxxxx` in the log. Endpoint: `/pqc/secure`.

Any JDK 25.0.5+ client offers X25519MLKEM768 by default. `curl` built with OpenSSL 3.5+ also negotiates X25519MLKEM768; clients without PQC support fall back to a classical group thanks to `client-negotiated`:

[source,shell]
----
curl --cert target/certs/pqc-client.crt --key target/certs/pqc-client.key \
     --cacert target/certs/pqc-client-ca.crt \
     https://localhost:xxxxx/pqc/secure
----

NOTE: The response text describes the hybrid key exchange; a classical client connected through the fallback does not get it.

----

=== Native Mode

IMPORTANT: Native mode requires having GraalVM and other tools installed. Please check the Prerequisites section of https://camel.apache.org/camel-quarkus/latest/first-steps.html#_prerequisites[Camel Quarkus User guide].

The native image must be built by a GraalVM / Mandrel release based on JDK 25.0.5 or newer, otherwise it lacks X25519MLKEM768 and fails at startup. On a JDK below 25 the `skip-native-below-jdk25` profile turns the native build and ITs off, even with `-Dnative`.

[source,shell]
----
mvn clean package -Dnative
./target/*-runner
----

== Testing

[source,shell]
----
mvn clean test
----

The tests call the server with the JDK TLS stack, restricting the named groups offered by the client:

* `PqcWithFallbackTest` (`client-negotiated`): hybrid client ✓, classical-only client (`x25519,secp256r1`) ✓, client without certificate ✗
* `PqcOnlyTest` (`strict`, via `PqcOnlyProfile`): hybrid client ✓, JDK default client ✓, classical-only client ✗ (TLS handshake fails), client without certificate ✗

Native mode runs `PqcWithFallbackIT` only, because a native executable is built with one configuration:

[source,shell]
----
mvn clean verify -Dnative
----

NOTE: The tests use RestAssured (Apache HttpClient) rather than `java.net.http.HttpClient`, because the latter ignores `SSLParameters.setNamedGroups()`.
