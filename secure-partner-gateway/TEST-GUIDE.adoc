= Secure Partner Gateway: manual test guide
:toc:

A step-by-step guide to try the `secure-partner-gateway` example by hand, from simple to complex. The gateway takes
orders from partner systems, authenticates and authorizes every call, keeps partners apart, validates, deduplicates and
rate-limits the orders, and writes a tamper-evident audit trail. The guide starts the application, gets the tokens and
then tests one behavior per section. It needs nothing from the README, all commands are here.

== Before you start

* Docker or Podman (the commands in this guide pick the runtime automatically). Dev mode starts Keycloak and PostgreSQL with Quarkus Dev Services.
* `curl`, `jq` and `uuidgen`.
* Free ports `8080` (gateway), `8082` (Keycloak) and `9876` (management).
* A Java 21+ JDK and Maven.

Open two terminals: one for the application (dev mode), one for the commands. Section 0 needs no running application.

=== 0. Hash-chain unit tests (no container runtime)

Goal: check the audit hash chain logic alone, without Keycloak, PostgreSQL or the application.

[source,shell]
----
mvn -f secure-partner-gateway/pom.xml test -Dtest=AuditChainTest,AuditLogTest
----

Expected result: `Tests run: 8, Failures: 0, Errors: 0` and `BUILD SUCCESS`. Run it from the root of the repository.

Proves: the chain code detects changed and removed records on its own.

== Start the application

In the first terminal, from the root of the repository:

[source,shell]
----
mvn -f secure-partner-gateway/pom.xml clean compile quarkus:dev
----

Start takes about 75 seconds (less when the images are cached). Wait for `Listening on: http://localhost:8080`.
Keep this terminal open: section 9 reads a log line from it.

== Get the tokens

In the second terminal. Tokens are short-lived: if a call answers `401` unexpectedly, run this step again.

[source,shell]
----
export TOKEN_URL=http://localhost:8082/realms/gateway/protocol/openid-connect/token
export ACME=$(curl -s -d grant_type=client_credentials -d client_id=partner-acme -d client_secret=acme-test-secret $TOKEN_URL | jq -r .access_token)
export GLOBEX=$(curl -s -d grant_type=client_credentials -d client_id=partner-globex -d client_secret=globex-test-secret $TOKEN_URL | jq -r .access_token)
export AARON=$(curl -s -d grant_type=password -d client_id=audit-console -d username=aaron -d password=aaron-test-password $TOKEN_URL | jq -r .access_token)
----

`ACME` and `GLOBEX` are partners, `AARON` is an auditor. Each section below ends with the audit view: the latest records
first. Look only at the new records of that section. Reading the trail is audited too (`AUDIT_QUERIED`).

== Tests

=== 1. No token and a tampered token

A call without a token and a call with a damaged signature must both be refused.

[source,shell]
----
export TAMPERED="${ACME%?????}AAAAA"
curl -s -o /dev/null -w 'no token: %{http_code}\n' -X POST http://localhost:8080/api/orders
curl -s -o /dev/null -w 'tampered token: %{http_code}\n' -H "Authorization: Bearer $TAMPERED" http://localhost:8080/api/orders/1
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`401` for both.

In the audit trail:

`AUTHZ_DENIED` (no token) and `AUTHN_FAILED` (bad token), both with the actor `anonymous`.

Proves: nothing gets in without a valid signed token, and the trail tells the two cases apart.

=== 2. Submit an order and retry it

Submit an order, then send the same request again with the same `Idempotency-Key`.

[source,shell]
----
export KEY=$(uuidgen)
for i in 1 2; do
  curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $KEY" \
    -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":2}' http://localhost:8080/api/orders
done
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`202` with an `orderId`, then `200` with the same `orderId`.

In the audit trail:

`ORDER_ACCEPTED` once, then `ORDER_REPLAYED`.

Proves: a retry does not create a second order.

=== 3. Tenant isolation

`acme` submits an order and reads it. `globex` asks for the same id.

[source,shell]
----
export ORDER_ID=$(curl -s -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":1}' http://localhost:8080/api/orders | jq -r .orderId)
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" http://localhost:8080/api/orders/$ORDER_ID
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $GLOBEX" http://localhost:8080/api/orders/$ORDER_ID
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`200` for `acme`, `404` for `globex` (same as for an unknown order).

In the audit trail:

`ORDER_ACCEPTED` and `ORDER_READ` for `acme`, and `ORDER_READ_DENIED` (outcome `DENIED`) for the `globex` read.

Proves: a partner cannot read, or even detect, the orders of another partner.

=== 4. Roles and unlisted paths and methods

A partner must not read the audit trail. A path or method that is not listed is denied even with a valid token.

[source,shell]
----
curl -s -o /dev/null -w 'partner reads audit: %{http_code}\n' -H "Authorization: Bearer $ACME" http://localhost:8080/api/audit
curl -s -o /dev/null -w 'auditor reads audit: %{http_code}\n' -H "Authorization: Bearer $AARON" http://localhost:8080/api/audit
curl -s -o /dev/null -w 'unlisted path: %{http_code}\n' -H "Authorization: Bearer $ACME" http://localhost:8080/api/unknown
curl -s -o /dev/null -w 'unlisted method: %{http_code}\n' -X DELETE -H "Authorization: Bearer $ACME" http://localhost:8080/api/orders/1
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`403`, `200`, `403`, `403`.

In the audit trail:

`AUTHZ_DENIED` for each of the three refused calls (actor `service-account-partner-acme`) and `AUDIT_QUERIED` (actor `aaron`) for the auditor.

Proves: roles are enforced and everything not listed is denied by default.

=== 5. Validation

Invalid orders must be refused with a clean error, without exception details.

[source,shell]
----
export KEY=$(uuidgen)
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $KEY" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":0}' http://localhost:8080/api/orders
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $KEY" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":1,"partnerId":"globex"}' http://localhost:8080/api/orders
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" -H "Idempotency-Key: short" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":1}' http://localhost:8080/api/orders
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`400` three times, each with an `application/problem+json` body (`"detail":"The request does not match the API contract"`, no exception details).

In the audit trail:

Three `REQUEST_REJECTED` records with outcome `REJECTED`.

Proves: input is validated strictly: quantity range, unknown fields and the key format.

=== 6. Header spoofing

The `acme` token comes with an `X-Partner-Id: globex` header. The tenant must still be `acme`.

[source,shell]
----
export ORDER_ID=$(curl -s -H "Authorization: Bearer $ACME" -H 'X-Partner-Id: globex' -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":1}' http://localhost:8080/api/orders | jq -r .orderId)
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" http://localhost:8080/api/orders/$ORDER_ID
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $GLOBEX" http://localhost:8080/api/orders/$ORDER_ID
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`200` for `acme`, `404` for `globex`.

In the audit trail:

`ORDER_ACCEPTED` and `ORDER_READ` for `acme`, `ORDER_READ_DENIED` for `globex`: the order belongs to `acme` although the header said `globex`.

Proves: the tenant comes from the token only, a client header cannot change it.

=== 7. Throttle

Send 30 parallel orders. The limit is 10 per second per partner.

[source,shell]
----
export RUN=$(uuidgen)
seq 1 30 | xargs -P 30 -I{} curl -s -o /dev/null -w '%{http_code} retry-after=%header{retry-after}\n' \
  -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $RUN-{}" -H 'Content-Type: application/json' \
  -d '{"sku":"WIDGET-1","quantity":1}' http://localhost:8080/api/orders | sort | uniq -c
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
sleep 2
----

Expected result:

A few `202` (about 10, the limit) and the rest `429` with `retry-after=1`. The split varies, for example 3 and 27, or 9 and 21.

In the audit trail:

One `ORDER_ACCEPTED` per `202` and one `REQUEST_REJECTED` per `429`. The view shows only the newest 20 of the 30 records, mostly `REQUEST_REJECTED`.

Proves: a partner cannot flood the gateway. The `sleep 2` lets the limit recover for the next section.

=== 8. Concurrent duplicates

Send 5 parallel orders with the same `Idempotency-Key`.

[source,shell]
----
export KEY=$(uuidgen)
seq 1 5 | xargs -P 5 -I{} curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $ACME" -H "Idempotency-Key: $KEY" \
  -H 'Content-Type: application/json' -d '{"sku":"WIDGET-1","quantity":1}' http://localhost:8080/api/orders
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

One `202` and four answers with the same `orderId`: `409` while the first request still runs, or `200` when it has already finished. On a fast machine you may see only `200`.

In the audit trail:

One `ORDER_ACCEPTED` only. The other requests add `ORDER_REPLAYED` (the `200` ones) or no order record (the `409` ones).

Proves: parallel duplicates create exactly one order.

=== 9. Audit chain

Ask the auditor to recompute the hash chain, and find the anchor line in the log.

[source,shell]
----
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $AARON" http://localhost:8080/api/audit/verify
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

Expected result:

`200` and `{{"valid":true,"checked":N}}`. In the dev mode terminal, look for a line like `Audit chain head: seq=N hash=...`. The application logs it at startup and every 5 minutes. Keep such a line outside of the database as an anchor.

In the audit trail:

`AUDIT_VERIFIED` for the verify call, then `AUDIT_QUERIED` for the view.

Proves: the chain is intact, and the logged head lets you detect removal of the latest records.

=== 10. The database is append-only

Goal: try to change the audit table directly in PostgreSQL. A trigger must refuse it, and the chain must stay valid.
The commands pick Docker or Podman automatically and read the real user, password and database name from the PostgreSQL Dev Services container.

[source,shell]
----
unset CTR PG
for c in podman docker; do id=$($c ps --format '{{.ID}} {{.Image}}' 2>/dev/null | awk '/postgres/ {print $1; exit}'); [ -n "$id" ] && { export CTR=$c PG=$id; break; }; done
if [ -z "$PG" ]; then
  echo 'no postgres container found: run podman ps / docker ps and check that the app is running in dev mode'
else
export DB_USER=$($CTR exec $PG printenv POSTGRES_USER)
export DB_PASSWORD=$($CTR exec $PG printenv POSTGRES_PASSWORD)
export DB_NAME=$($CTR exec $PG printenv POSTGRES_DB)
echo "runtime=$CTR container=$PG user=$DB_USER database=$DB_NAME"
$CTR exec -e PGPASSWORD=$DB_PASSWORD $PG psql -U $DB_USER -d $DB_NAME -c "UPDATE audit_event SET outcome = 'SUCCESS' WHERE seq = 1"
$CTR exec -e PGPASSWORD=$DB_PASSWORD $PG psql -U $DB_USER -d $DB_NAME -c "DELETE FROM audit_event"
fi
curl -s -w ' %{http_code}\n' -H "Authorization: Bearer $AARON" http://localhost:8080/api/audit/verify
curl -s -H "Authorization: Bearer $AARON" 'http://localhost:8080/api/audit?limit=20' | jq -r '.[] | [.seq, .ts, .action, .outcome, (.actor // "-")] | @tsv'
----

For an interactive session, run `$CTR exec -it -e PGPASSWORD=$DB_PASSWORD $PG psql -U $DB_USER -d $DB_NAME` and type
the statements there.

Expected result: the line prints the runtime, container id, user `quarkus` and database `quarkus` (the Dev Services defaults; the password is `quarkus` too). `UPDATE` fails with `ERROR:  audit_event is append-only, UPDATE is not allowed`, `DELETE` with `ERROR:  audit_event is append-only, DELETE is not allowed`. Verify still answers `200` and `"valid":true`.

In the audit trail: only `AUDIT_VERIFIED` and `AUDIT_QUERIED` (actor `aaron`) are new. The refused statements change nothing.

Proves: the database itself refuses changes and deletes of audit records, and the chain stays valid.

== Clean up

Stop dev mode with `q` or Ctrl+C in the first terminal. Then check that the Dev Services containers are gone:

[source,shell]
----
[ -n "$CTR" ] || for c in podman docker; do $c ps -q >/dev/null 2>&1 && { CTR=$c; break; }; done
$CTR ps
----

The list must show no `postgres` and no `keycloak` container. Remove leftovers with `$CTR rm -f <id>`.
